Screen 2 Trace one action: opening the homepage

Follow what happens from the moment you type the address. Most people never look past step 2 — the surprise is in steps 3–5.

1
You type the URL

Your browser asks a DNS server where globalpeaceyes.org lives, then opens a connection to that server.

2
The server sends index.html and friends

Seven HTML pages, one big CSS file, fonts, images, and ~35 JavaScript modules.

3
The browser starts painting the HTML it got

This is the "first paint" — the rough version you'd see for a few hundred milliseconds.

4
A script decides the handover

script_main reads a JSON label on the page, picks a route, and fetches that route's JavaScript.

5
React rebuilds the visible page

The JavaScript replaces most of the HTML with its own version. That's the page you actually interact with.

Screen 3 The file tells you its own secret

Near the top of index.html, inside <body>, sits a single div labelled id="main". Read its attributes and it confesses the entire plan.

code 
<div id="main"
  data-framer-hydrate-v2='{"routeId":"augiA20Il","localeId":"default","breakpoints":[{"hash":"72rtr7","mediaQuery":"(min-width: 1728px)"},{"hash":"1pz11xk","mediaQuery":"(min-width: 1440px) and (max-width: 1727.98px)"},{"hash":"dv7j5c","mediaQuery":"(min-width: 1200px) and (max-width: 1439.98px)"},{"hash":"1wmt56v","mediaQuery":"(min-width: 810px) and (max-width: 1199.98px)"},{"hash":"1522l99","mediaQuery":"(max-width: 809.98px)"}]}'
  data-framer-generated-page
>
plain english

This div is the whole React app. Everything visible on the page lives inside it.

hydrate = the app may take the already-painted HTML and wire it up, instead of redrawing everything.

routeId augiA20Il = "which page am I?" — a short code for the homepage's component file.

5 breakpoints = 5 screen sizes (1728, 1440, 1200, 810, ≤809px) shipped simultaneously in one file.

💡
Key insight — the HTML is a placeholder, not the page

This file is ~357 KB and describes a ~96 KB page. The runtime throws away most of what the browser first painted and rebuilds it from JavaScript. When you read a Framer export, "what's in the HTML" is not "what the user sees."

🔎
Good to know — chunked delivery

Only script_main (6 KB) loads eagerly. The framer runtime, React, and the page's own code are all dynamically imported — pulled on demand, in parallel, by the browser. That's the "modulepreload" trick.

💡
The word to know: hydration

Framer pages ship ready-made HTML so they look right instantly. Hydration is React "taking over" that ready-made HTML instead of redrawing it — it keeps what's painted and attaches behavior. It's like buying a furnished flat: the furniture is already in, you just turn on the lights and connect the wifi.

Screen 3 The actual decision code

All that conversational booting is just a few lines in script_main. This is the real decision point — hydrate the existing HTML, or rebuild from scratch?

code 
if (e) c = JSON.parse(t.dataset.framerHydrateV2);
else { /* read route from the URL path */ }
let l = z({ routeId: r, localeId: i, pathVariables: a });
let u = await l;
e ? (
  O("framer-rewrite-breakpoints", prune, () => {
    S(); y(); _(t, u, { onRecoverableError: n })  // hydrate
  })
) : g(t, { onRecoverableError: n }).render(u)  // fresh render
plain english

if (e) … — if the HTML carried a hydrate note (it did, in Module 1), read it.

else … — no note? Figure out the route from the web address instead.

z(...) — go build the page component for this route. Returns a promise.

await l — wait for that component to be ready.

Prune first. The runtime strips the non-current breakpoints from the first paint.

_(t, u) = hydrate — attach React to the cleaned HTML.

g(...).render(u) = plan B — if hydration isn't possible, render the page from scratch.

onRecoverableError is the safety net — you'll meet it in Module 6, when things go wrong.

04

The outside world — and the chunk that drifts

Framer serves the real application from its own CDN, not from your server. That split explains the site's biggest bug.

Screen 1 What your server sends vs what the browser fetches

Your HTML names files on framerusercontent.com. When the browser reads the skeleton from Module 2, it treats the homepage as a nightly concert: your server provides the venue (HTML + CSS), but the headliner (React) arrives by tour bus from the CDN.

🏠

Your server

site.css (1.24 MB), site.js, site-end.js, fonts.css, the SVG sprite.

⚛️

react.DjGraiHU.mjs

React 19 + react-dom. 144 KB. Loaded from the Framer CDN.

🎬

framer.1egicfVa.mjs

The runtime. 464 KB. Router, components, animations.

📦

page chunk

LBrkLi3nuk….CD3oeThu.mjs — the homepage's own component code.

Total runtime payload across all pages: React + runtime + route chunks ≈ 760 KB of JavaScript — before you count videos, embeds, and widgets.

  fetchpriority="low"
  href="https://framerusercontent.com/sites/
    21Hkz9s2D8H7aNrnx45o3p/react.DjGraiHU.mjs"

plain english

modulepreload — tell the browser "you'll want this file soon, fetch it now."

fetchpriority="low" — don't compete with the first paint; download lazily.

🔎
A wrong attribution that was caught

The 2.15 MB of Cloudflare Turnstile traffic on the homepage was originally blamed on the site's own code. It's actually Vimeo's own bot protection, one instance per film embed. Read the frame attribution before you quote a "CAPTCHA on our homepage" metric.

Screen 3 The problem: chunk drift

Here's the twist. The exported HTML expects a specific version of each CDN file — the file names are locked by a content hash. But the CDN has since published newer builds under the same names. Identical filename, different bytes.

2016

Export downloaded to this repo, hash-locked chunk names.

→
CDN

Framer republishes; the same URLs now point at new code.

→
Browser

HTML and JS no longer describe the same page. React notices.

Result: 6 of the 12 chunks on index.html differ from the local copies — including the homepage's own page chunk, which differs by 443 KB.

⚠️
This is why "it worked when we exported it" is not true later

The content hash in the filename is meant to guarantee stability. With a frozen export, the guarantee points backwards — to code that's no longer at the URL. Hydration then throws the served DOM away and re-renders from JavaScript on every page view. That's the bug you meet next.

05

The clever tricks

Framer is full of small engineering gambits. Three of them make this frozen site exceptional — and fragile.

Screen 1 Trick #1 — ship 5 layouts, keep 1

A Framer page contains all five breakpoints in one file (that's the five-part list in Module 1's JSON). Every element is stamped with which variants it appears in.

code 
<div data-framer-root class="framer-fu3UK …
  framer-72rtr7 pc-i-058">

  <!-- only mobile has this hero → hidden everywhere else -->
  <div class="ssr-variant hidden-1pz11xk
    hidden-dv7j5c hidden-1wmt56v hidden-1522l99">
      …mobile-only content…
  </div>
plain english

The root div carries a class naming the active layout (framer-72rtr7 = ≥1728px).

Every responsive copy is in the file at once, marked ssr-variant.

Each variant is stamped with the breakpoints where it's hidden (hidden-1pz11xk = invisible at 1440px, etc.).

So at 1728px the browser first paints the ≥1728 copy and the four others — then the runtime deletes the hidden ones.

💡
Why ship the dead layouts at all?

Framer bakes every breakpoint into the served HTML so the first paint is correct no matter the device — no JavaScript needed. The cost: every page carries ~4× the layout it will actually keep. The runtime prunes the extras after load.

Screen 2 Trick #2 — the appear animations

The hero elements start almost invisible (opacity: 0.001) and "spring" into place. Framer stores that choreography as JSON in the HTML, and an inline script plays it back with the Web Animations API before React ever loads.

code 
"d5kl3q": {
  "default": {
    "initial":   { "opacity":0.001, "x":0, "y":-16, "scale":1 },
    "animate":   { "opacity":1,  "x":0, "y":0,
                   "transition": { "type":"spring",
                     "bounce":0.2, "duration":0.4 } }
  }
}
plain english

Each animated element has an id and this recipe in the inline payload.

initial — 0.001 opacity (≠ 0, so search engines still "see" the text), nudged up 16px.

animate — spring to full opacity and place.

spring, bounce 0.2, 0.4s — a natural, bouncy feel, matching the original design timing.

The trick is the handoff: the inline script runs the first animation pass, then exposes a global MotionHandoff so the runtime can take over the same animations without restarting them. Only transform and opacity are animated — the two properties that stay smooth on the GPU.

Screen 3 Trick #3 — SVG icons injected at runtime

Every icon on the page is an <svg><use> pointing at assets/svg/sprite.svg#id. But notice what's in the served HTML:

code 
<div
  id="svg-templates"
  aria-hidden="true"
  class="pc-i-040">
  <!-- served empty; the icon defs arrive later, injected by the runtime -->
</div>
plain english

#svg-templates is Framer's icon pantry — served empty.

After hydration the runtime fetches the sprite file, re-injects the icon definitions in here, and points every <use> at them.

The catch: the definitions actually come from the CDN page chunk. If the runtime is blocked, most icons disappear (we kept 3–9 per page from the local sprite).

🔎
The file is redundant — but blocking it changes nothing

The runtime fetches sprite.svg and re-injects its defs into #svg-templates. Block that file and nothing changes; block the runtime and icons vanish. When you read "the sprite is a dependency", you must ask: a dependency of what?

06

When things break

The exported site has one visible flaw and one invisible one. Meet both — then try to spot a bug yourself.

Screen 1 The 4 errors per page

Remember Module 4's chunk drift? Because the served HTML and the CDN chunks disagree, React can't trust the first paint. Every page view throws four recoverable errors — and falls back to plan B (rebuild from scratch).

code 
console.warn(
  `Caught a recoverable error. The site is still
   functional, but might have some UI flickering or
   degraded page load performance. … server/client
   mismatches: `, e, r);
B(
  `published_site_load_recoverable_error`,
  { message: String(e), componentStack: r }
);
plain english

console.warn — the console message you'd actually see: React #418 (server/client mismatch) and #423 (root switches to client render).

"recoverable" — the site still works; it just rebuilds itself from JavaScript.

B(...) — the error is also pushed to window.__framer_events for analytics.

💡
What "recoverable" really costs

On our export the recoverable path triggers a full client re-render on every load — the DOM you first painted is thrown away. Up to the visible results: 6 of 7 pages lay out 2750 px wide at a 1440 px viewport because a flex team stretches past the screen. privacy-policy.html is the only clean page.

Screen 2 Spot the bug

Here's a real, hand-tuned block from this project's own CSS rules — the mobile nav. One line is wrong. Click it to check, and read the reveal.

1.nav { position: fixed; top: 0; z-index: 2; }
2.nav::after {
3 inset: 0; content: "";
4 border-bottom: 1px solid #fff;
5 position: absolute;
6}
🔎
Why this matters for you

On the live site, that underline is #222 (near-black); painted white, the header line vanishes against a light page. Off-by-one shade, visually dramatic. When you steer an AI agent, "match the header underline" is only enough if you also say what colour trumps the rest of the header.

Screen 3 When you block the runtime entirely

The acid test: what if the CDN is unreachable? The good news — the page still renders and lays out correctly. The catch — the table of losses is a map of everything the runtime owns.

✅

Survives

Nav links, text, layout (with the caveats above). First paint from the HTML alone.

🧩

The app code

The page chunk imports the CDN's React + runtime. No CDN → no app → no interactivity.

💀

Dies first

Most SVG icons (only 3–9 survive), 21 of 26 hero animations (stuck at opacity 0.001), the vote counter sticks at LOADING.

The lesson: "it's a static site" was true only if you also meant "static HTML + remote JavaScript you don't control." That's the tension this whole repo is about.

Screen 2 The 4.55 MB → 1.22 MB cleanup

The owners knew this. So they set out to slim the served files — without touching what the runtime needs. The numbered moves are the story of a careful, measurable cleanup.

1
Extract inline CSS

17 <style> blocks → one shared site.css. Heads dropped from ~135–225 KB to ~3.5 KB.

2
Externalise inline SVG

Data-URI artwork → uri_1-3.svg, shared icon defs → sprite.svg. Saved ~1.45 MB.

3
Inline styles → classes

2,557 repeated style="…" → generated .pc-i-NNN rules in site.css. ~470 KB removed.

4
Strip editor metadata

Framer-editor-only attributes removed (~116 KB). Runtime-required attrs carefully kept.

5
De-duplicate inline scripts

5 identical blocks → site.js (head) + site-end.js (body tail). −29 KB, +4 KB cacheable JS.

code 
/* in index.html, 749× this class name is served */
<div class="pc-i-043"></div>

/* …in site.css, its rule is a single declaration: */
.pc-i-043 { display: contents }
plain english

The cleanup replaced thousands of repeated inline styles with numbered classes, pc-i-NNN.

display: contents — this element simply "opens" its children into the flow, adding no box of its own. It's a layout helper.

The honest catch: after hydration the runtime's React render ignores these — the served count (749) drops to 1 in the live DOM. The savings are pure transfer weight.

🔎
Do not deploy the current export as-is

All that cleanup makes the files smaller — but remember the runtime re-injects the metadata and generates its own classes after hydration. The transfer savings are real; the rendering bug is not fixed by cleanup. Smaller ≠ fixed. That's why this course separates "what's in the file" from "what the browser ends up with."
